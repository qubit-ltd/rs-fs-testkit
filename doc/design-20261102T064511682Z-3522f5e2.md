## 2. 架构选择与不变条件

继续使用“独立 fixture → 有状态 suite → 公开 qubit-fs 门面”的现有架构。报告状态机、check ID、注册宏、取消探针和恢复所有权机制均保持现有职责。只修正具体错误和文档边界，不引入新的公共 API、运行时依赖或公共探针。

比较过的方向：

1. **局部修复，保留 path 依赖，项目维护准备清单（采用）。** 改动小，保留本地与下游开发的依赖来源；对清单的 bootstrap 所有权作显式调整，避免反复回归。
2. **全部改用 registry 依赖。** 根 crate 与独立 S3 crate 必须一起考虑，且本地集成可能需要额外 patch 来统一 qubit-fs 类型来源。会扩大依赖解析和锁文件变化，不作为本轮方案。
3. **重构统一载荷框架、清理注册框架或源错误访问 API。** 对本轮错误没有额外必要收益，不采用。

不做兼容性破坏。rs-fs-local 的两个同步 fixture 和示例无需迁移；S3 fixture 的内部观察行为修正无需公共调用方迁移。FST-002 会让原先被误判的合法空写通过，但不会把缺失证据降级为跳过。FST-005 保留当前锁语义，只公开必要使用约束。

## 3. FST-001：恢复依赖准备并明确配置所有权

### 事实

- `Cargo.toml:38`：`qubit-fs = { path = "../rs-fs", version = "0.3", ... }`。
- `.infra/ci/local-path-dependencies.tsv` 当前仅有注释。
- `.infra/bootstrap-update.toml` 当前启用 `local-path-dependencies-default`，该 profile 的模板恰好是空清单。
- `.infra/bootstrap-source.json` 当前将该 TSV 登记为受管文件；仅编辑 TSV 会使 bootstrap-check 报漂移，默认更新也会覆盖它。
- 当前共享 prepare helper 按 TSV 克隆依赖，没有自动解析 Cargo path 的补偿逻辑。现有同级 rs-fs 进一步 path 依赖 rs-redact；rs-redact 的 derive 成员在同一 checkout 内。

### 决策

把 TSV 转为项目自有配置，不修改共享基础设施仓库，不编辑共享 helper，不改变 Cargo 依赖来源。

1. `.infra/bootstrap-update.toml` 的 `profiles` 从现有数组中仅移除 `local-path-dependencies-default`；当前结果为 `profiles = []`。
2. `.infra/bootstrap-source.json` 的 `files` 映射中仅移除 TSV 这一项，将其明确移交项目维护。保留其余记录、摘要、来源版本与用户已有修改；不能给自定义内容伪造上游摘要。
3. TSV 恢复实际需要的仓库行。按当前源码，最低集合为 `../rs-fs` 与 `../rs-redact`，URL 分别是 `https://github.com/qubit-ltd/rs-fs`、`https://github.com/qubit-ltd/rs-redact`，沿用既有 `main` 分支约定。实施时沿实际 manifest 复核 Cargo 解析所需闭包，只有出现真实外部 path 依赖才补充相应仓库；不照搬原五行清单或其他项目的清单。
4. 在 TSV 注释中说明项目维护、path 依赖闭包以及不要启用空清单 profile。将对 profile、快照所有权与 TSV 的修改作为同一个审查单元。

这样与 bootstrap 的“未选择 profile 的配置由项目维护”模式一致。实施不运行全量 `update-infra.sh` 来附带升级无关基础设施。用已安装工具的只读 snapshot 检查确认其余受管文件未漂移；必要时在可丢弃副本中验证 sync 的选择逻辑不会把 TSV 重新纳入受管集合。

### 验证边界

必须在没有预置 sibling 的临时文件系统沙箱中复制最终工作树，运行真实 prepare 入口，再运行本 crate 的 locked metadata/check。沙箱只是临时测试目录，不是新的 Paseo workspace；不挪走、删除或覆盖用户现有 sibling。记录实际克隆 revision、依赖来源及锁文件前后摘要。解析失败不得以本机 sibling 环境的通过代替。分支漂移导致版本或锁文件不匹配时，先记录原因，再在本条范围内选择兼容 revision 或清单项，不顺手更新整个依赖生态。

## 4. FST-002：有界强化写载荷

修改范围为同步和异步的 `write_guarantee.rs`，以及各自现有 I/O 回归测试文件。

两条执行路径均复用各自 `write.rs` 中已有 `bounded_payload`。优先载荷仍为 `b"b"`；`Maximum(0)` 使用空 slice，`Maximum(1)` 及更大、未知、不适用、无界上限保持一字节行为。采用局部拥有的 Vec，再借用其 slice，保持后续 fixture 准备、载荷不变校验、写入和独立观察逻辑不变。

`AtomicReplace` 继续通过独立 seed 预置 `b"a"`，因此空新载荷仍可验证替换和旧内容消失。`Durable` 继续要求 CreateNew 与 Required durability，空文件创建同样必须产生可独立读取的目标。不得用 `NotApplicable`、`SkippedOptional` 或 `Unverified` 回避这两项能力的正向检查。

每种驱动分别对 `WriteAtomicReplaceExisting`、`WriteDurable` 在 `Maximum(0)` 和 `Maximum(1)` 下使用全新 fixture 和 suite，断言完整 `ContractRun::assert_satisfied()`，并逐 ID 确认结果恰为 `Passed`。现有坏 provider 检测回归继续通过，确保没有削弱原子性、持久性或内容检查。测试按具体 check 运行，避免把其他未纳入本条的 Write 子检查假定为已支持所有零边界。

## 5. FST-003：观察与删除所有权分离

只修改独立 S3 crate 的 `tests/common/fixture.rs` 和 `tests/s3_listing_tests.rs`。

保留现有 `path()` 对准备/即将创建目标的登记行为；这些调用保证失败后仍可清理目标。本次只将 `snapshot_namespace_paths()` 内的 `self.path(logical)` 改为无登记的 `Path::parse_literal(logical)`，保留 namespace 边界检查及 `FixtureError` 错误链。

回归使用 InMemory store：

1. 通过独立 SDK 直接放入当前 namespace 的 `sentinel`，不调用 fixture 的 `path()` 或 seed hook。
2. 通过 fixture seed 另一个归其所有的对象。
3. 两次读取快照，均包含这两个逻辑路径；两次 teardown 后，owned 对象均不存在，而 sentinel 的原始字节仍在。
4. 原有 namespace 边界和 supported contract matrix 继续运行，避免修复导致列表遗漏或 owned 对象泄漏。

影响范围严格限本次子 namespace，不声称存在共享父 prefix 批量删除问题。测试不访问真实服务，不新增凭据要求；真实服务 ignored 测试不作为本轮必需成功证据。

## 7. FST-005：公开持锁和不可重入约束

在 `ContractSource::inspect` 的英文 Rustdoc 增加锁语义：闭包在持有该 source 的内部互斥锁时同步执行，不能直接或间接重入同一 source 的 `inspect`/`take`，也不能等待另一个需要该锁的操作。

示例将类型判断结果返回到闭包外，再调用 `take()`。须说明二者不是原子操作：并发调用者可能先取走 source，因此仍需处理 `take() == None`。取走 source 仍转移显式恢复责任，不改变失败历史。

不改为 `try_lock`，不新增公开访问 API，不将 source 临时取出后再放回。上述方向会改变并发语义且不是补正文档所必需。测试只验证安全使用路径，不编写可能永久阻塞测试进程的重入测试。
